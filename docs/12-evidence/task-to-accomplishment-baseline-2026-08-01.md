> **Baseline freeze:** 2026-08-01 17:11:39 +07:00

> **Authority:** this document records the current implementation; it does not replace the master

## 1. Executive conclusion

Suar already has useful pieces of the lifecycle—rich task columns, task assignment/submission
snapshots, governed review confirmation, work-history facts, profile snapshots, and talent filters—but
they do not yet form one immutable, attributable chain from requirement to verified accomplishment.

The most important baseline findings are:

1. The primary task-authoring surface is the project-board modal, not the standalone create page. It
   collects a substantial but incomplete subset of the rich task model and enforces an artificial
   four-category skill mix.
2. A title/link-only Draft cannot currently be saved through the normal create contract. Conversely,
   current readiness checks do not prove that a Task is self-contained or that its future evidence
   contract is usable.
3. Assignment and submission snapshots are partial. Task detail still renders mutable task data, so
   the assignee/reviewer does not have the target resolved, pinned Task Specification and Work/Evidence
   Contract.
4. Review confirmation is durable and retry-aware, but its structured facts are rating-centric. It
   cannot yet confirm, narrow, reject, or attribute action/object/ownership claims per contributor.
5. Existing work-history/profile/search surfaces can show skills, scores, titles, and some task
   metadata. They cannot reliably prove statements such as “designed the pre-order API,” “scaled a
   database,” or “debugged a production incident.”
6. Historical profile facts are partly rebuilt by joining mutable `tasks`; this creates semantic drift
   risk after later task edits.
7. No target TC-TVA scenario is complete at baseline. Existing tests are valuable regression anchors,
   not proof of the new end-to-end feature.

The implementation therefore needs an additive, versioned seam:

```text
Project Context / Work Package
        -> Task Specification + Work/Evidence Contract versions
        -> resolved assignment snapshot + acknowledgement
        -> Completion Report + per-user claims + evidence mappings
        -> structured Review Observations
        -> immutable Verified Accomplishment
        -> privacy-safe Profile / Capability Signal / Talent Search projections
```

assignee, due/parent/time, role, skills, acceptance, context, role/domain/problem, technology,
learning, and tags. It does **not** currently send the full target set, including expected
deliverables, measurable outcomes, impact scope, environment, collaboration type, complexity notes,
autonomy, and estimated users affected.

Client validation requires title, status, project, skills, and acceptance criteria. Backend rules also
require at least one skill and one skill in each of Technology, Engineering, Soft Skill, and Delivery.
When semantic level IDs are absent, one selected level can be copied into min/target/ceiling. These
behaviors conflict with FR-TVA-001, FR-TVA-009/010 and BR-TVA-018.

`inertia/apps/user/modules/tasks/create.svelte` has a readiness card but is not the primary routed
authoring experience. Implementing only that page would leave the real project-board flow unchanged.

### 4.4 Review and projection trigger

| Layer        | Current entry point                                              | Baseline behavior/gap                                                                   |
| ------------ | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Review page  | `start/routes/projects.ts`: `/projects/:projectId/reviews/tasks` | Renders `inertia/apps/user/modules/reviews/task-board.svelte`                           |
| Task panel   | user/org `task_review_workflow_panel.svelte`                     | Drives existing task-review workflow                                                    |
| Mutations    | `start/routes/reviews.ts`                                        | Submit/accept/respond/report/confirm/evidence/self-assessment/dispute families          |
| Confirmation | review confirm controller/command                                | Stages `ReviewConfirmed`                                                                |
| Projector    | `ProcessReviewConfirmedEventCommand`                             | Receipt/idempotency, authoritative source check, DB projections, external-effect cursor |

`ProcessReviewConfirmedEventCommand` is the correct durability pattern to preserve. It claims a
receipt in a transaction, acquires projection locks, verifies authoritative state, updates credibility,
skill/performance/trust/profile aggregates, then resumes external effects with a cursor. A new
accomplishment must be created inside an equally durable, versioned database phase (or by its own
durable outbox consumer), never as an untracked post-confirmation callback.

Existing review facts primarily capture scores and evidence metadata. They do not make the reviewer’s
decision about an exact contributor claim, ownership, capability observation, ceiling, confidence,
rationale, and privacy classification first-class.

## 12. Abnormal-condition and negative-path starter

Each worker must preserve at least the following classes in its TDD matrix:

- inaccessible/authenticated/expired/deleted links; encrypted, unsupported, oversized, malicious, or
  partially uploaded files;
- critical image without text, long filler text, XSS-rich content, uncertain import mapping;
- cyclic/cross-tenant/stale inheritance; empty override; archived parent version;
- duplicate submit, concurrent autosave, stale optimistic version, offline refresh, idempotency retry;
- material edit during review/dispute; reassign/deactivate assignee; conflicting active assignment;
- missing/N/A criterion, expiring/deleted/confidential evidence, orphan upload, notification failure;
- contributor disagreement, ownership inflation, self-review/conflict, missing quorum;
- duplicate/out-of-order events, crash at DB/external boundary, replay/rebuild hash mismatch;
- dispute after publication, correction/revocation, tenant/user/source deletion;
- private-term leakage through candidate existence, count, facet, snippet, ranking, or explanation;
- public wording inflation, legacy/retrospective mislabeling, missing/rotated snapshot access;
- keyboard-only/mobile/focus recovery and screenshot-before-semantic-assertion false passes.
