## Non-removable predicates

The following predicates are security/authority constraints, never chips users can clear:

- tenant, current organization/project and actor identity;
- entity deletion/active status where the domain treats it as non-discoverable;
- task visibility, unassigned/application-open rules and actor application state;
- talent active/searchable status plus public-only evidence/work history;
- task creator/assignee/member/elevated-role permission scope;
- organization membership/joined/available projections;
- audit system/org/actor scope and allowed target IDs;
- notification recipient identity;
- project candidate eligibility and existing-member exclusion.

They must be composed before user criteria, totals, facets, suggestions and fallback. Permission
version/scope must be present in caches and cursor/session evidence. A provider failure may not drop
one of these predicates or return a broader SQL fallback.

## Baseline risks carried into implementation

1. Bounded-window client filtering and counts can look complete while omitting off-page records.
2. Tags/technology stack use singleton substring semantics instead of canonical multi-value
   Any/All/None/At-least-N semantics.
3. Search fallback changes rank and can change membership on deeper candidate windows.
4. `recommended` Marketplace sort has a suspicious policy branch: actors allowed to use it are
   rewritten to `created_at`, while the other branch retains `recommended`; freeze behavior in RED
   tests before changing it.
5. Some ranked SQL ordering interpolates index-originated candidate IDs into raw order expressions;
   bind values when the owning package touches those paths.
6. Candidate pickers lack debounce/cancellation/stale-response fencing.
7. Existing proof is dominated by unit/integration tests. It does not close the role-based UI,
   screenshot, no-leakage, degraded-provider, complete-population or side-effect evidence gates.
